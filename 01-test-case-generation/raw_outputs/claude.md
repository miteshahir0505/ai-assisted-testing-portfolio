# Assumptions
Since the user story doesn't specify these details, the following assumptions were made to write concrete, testable steps. These should be validated against actual requirements/design before execution:

1. **Error message wording** is not specified — tests assume a "generic" (non-specific) message is the secure/expected behavior for invalid credentials, but the actual expected text should be confirmed with the team.
2. **Field length limits** for username/password are not specified — boundary test cases use illustrative values (e.g., 500+ characters); actual max-length limits should be confirmed and test data adjusted accordingly.
3. **Case sensitivity** of the username field is not specified in the story.
4. **Lockout policy** (number of failed attempts before lockout, lockout duration) is not detailed — the story only states a locked-out user cannot log in, so TC_30 assumes some rate-limiting/lockout-triggering mechanism may exist and should be confirmed.
5. **Whitespace-trimming behavior** (leading/trailing spaces) is not defined in the story — TC_09 flags this for clarification rather than assuming a fixed behavior.
6. **Session/token mechanism** (cookies, JWT, etc.) used for authentication is not specified — bypass-related tests (TC_19–TC_22) are written generically and may need tool-specific adjustment (e.g., Burp Suite/Postman for replay attacks).
7. **Autocomplete/autofill policy** for the password field (allowed or disabled) is not specified in the story — TC_25 and TC_26–TC_28 assume standard browser autofill is permitted; confirm if the app explicitly disables this for security reasons.
8. **HTTPS enforcement** (TC_32) is assumed as a standard security expectation, not explicitly stated in the story.
9. Only two fields (username, password) are assumed to exist on the login form, with no additional elements (e.g., CAPTCHA, MFA, "remember me" checkbox) since none were mentioned in the story.
